## 3. 논의 내용

### 안건 1. 확인 화면 `PATCH /scans` 규칙

- 프론트는 안 바꾼 칸을 요청에서 빼고 보내고, `null`은 보내지 않습니다.
- `dose_per_time`·`dosage`에 `null`이 오면 무시하지 않고 422로 돌려줍니다. `null`이 온다면 프론트 버그라서, 조용히 넘어가면 회원이 고친 값이 저장되지 않아도 모르기 때문입니다.
- 1회 용량 칸을 비우면 `{"text": ""}`로 보냅니다. 읽을 수 없는 용량과 같게(`parsed: false`, `needs_check: true`) 처리합니다.
- 복용 조건을 "선택 안 함"으로 되돌리는 동작은 두지 않습니다.
- 용량 빈칸 확정: 명세 4장(빈칸 불가)과 6장(필수 아님)이 서로 달라서 정리했습니다. "적당량"처럼 글자가 있으면 읽지 못해도 확정할 수 있고, 완전히 빈칸이면 확정할 때 422로 막습니다. 가이드의 먹는 법 문장에 용량이 꼭 들어가야 하기 때문입니다.

### 안건 2. 리프레시 토큰 만료 방식

- 재발급할 때마다 만료일도 새로 14일로 잡습니다. 14일 안에 한 번이라도 들어오면 로그인이 유지되고, 14일 동안 쓰지 않으면 다시 로그인합니다.
- 매일 여는 복약 앱이라 2주마다 로그인이 풀리면 복약 체크를 놓칠 수 있습니다. 토큰 교체와 재사용 감지가 이미 있어서 보안 장치는 충분합니다.
- 만료·무효화된 `refresh_tokens` 행 정리는 이슈 #51로 남겼습니다.

### 안건 3. 422 에러 형식과 에러 코드

- 프론트 `client.ts`는 에러 본문에 `code`가 없으면 전부 "잠시 후 다시 시도해 주세요"로 처리합니다. FastAPI 기본 422는 `code`가 없어서 어느 칸이 틀렸는지 화면에 못 보여줍니다.
- 명세 1-1 형식으로 바꿉니다: `{"code": "VALIDATION_ERROR", "message": "입력한 내용을 확인해 주세요", "fields": {...}}`
- 칸 이름은 명세 4장 공통 규칙대로 목록 순번을 대괄호로 씁니다(예: `drugs[0].dose_per_time`). 숫자는 요청으로 보낸 목록의 순서(0부터)입니다.
- 칸별 문구는 서버가 한국어로 보내고, 프론트는 그대로 띄웁니다.
- 에러 코드는 글자로 쓰지 않고 `ErrorCode` Enum으로 모읍니다.
- 위 내용은 #52로 올라왔습니다.

### 안건 4. 빠진 약 알림 화면

- LLM이 약 줄을 통째로 빠뜨리면 `drugs`에 그 줄이 없어서 칸 신뢰도로는 잡을 수 없습니다(테스트 처방 Case 10). OCR 줄과 LLM 결과를 맞대 보고, 약 DB에 비슷한 약이 있는 줄만 알립니다.
- 화면: 약 목록 맨 위에 노란색 배너로 "빠진 약이 있을 수 있어요" + 해당 원문 줄. 버튼은 [이 약 추가하기](매칭된 약 미리 채움) / [괜찮아요].
- 회원이 같은 `drug_id`의 약을 추가하면 서버에서 알림을 지웁니다. [괜찮아요]는 화면에서만 닫습니다. 알림이 있어도 확정은 막지 않습니다.
- 2단계 결과에 매칭된 약의 `drug_id`도 같이 담기로 했습니다(서비스 연결 PR에서).

### 안건 5. 폴더 구조와 머지 순서

- 프론트: FSD v2.1 Pages First 방식. 한 화면에서만 쓰는 코드는 `pages/화면이름/` 안에 두고, 두 화면 이상에서 쓰게 되면 그때 `widgets`·`features`·`entities`로 꺼냅니다. 다른 층은 `@/` 경로로 가져옵니다.
- 백엔드 테스트: `app/tests/기능이름/` 안에 둡니다. 같은 기능 테스트끼리 쓰는 가짜 객체는 그 폴더의 `fakes.py`에 둡니다.
- 기능 이름: `auth`, `user`, `scan`, `prescription`, `guide`, `chat`, `drugs`. 백엔드 테스트 폴더와 프론트 `pages` 슬라이스 이름을 맞춥니다. 공용 코드(`app/core/`) 테스트는 `app/tests/core/`에 둡니다.
- 머지 순서: 테스트 폴더 정리 PR을 먼저 머지하고, #52는 dev를 받아와서 명세서 충돌과 `test_exceptions.py` 위치(`app/tests/core/`)를 정리한 뒤 머지합니다.

### 안건 6. 커밋 나누기

- 한 커밋에 성격이 다른 작업이 섞이면 되돌리기와 리뷰가 어렵습니다. 특히 리팩터링(동작 그대로)과 동작 수정이 섞이면 "동작이 그대로인지" 확인하기 어렵습니다.
- PR 하나 안에서도 작업별로 커밋을 나눕니다. 이슈가 두 개면 커밋도 두 개입니다.
