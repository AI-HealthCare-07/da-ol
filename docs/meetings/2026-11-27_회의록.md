  - 이유: 운영진 가이드·레포 배포 틀과 같은 구조, 명세 4-1에서 걱정한 30MB 업로드·SSE 프록시 통과 문제를 nginx 설정으로 직접 해결(Plan B 불필요), 멘토님 Vercel 비추천
- 바뀌지 않는 것: 프론트 API 상대 경로(`/api/v1/...`), 쿠키 `SameSite=Lax`·호스트 전용, CORS 설정 없음, 카카오 Redirect URI(`https://daol.site/auth/kakao/callback`)
- 배포 틀에서 고칠 것
  - `redis`, `ai-worker` 서비스 제외 (안건 2)
  - nginx: 프론트 빌드 파일 내보내기(모든 주소를 `index.html`로), 업로드 크기 제한 30MB(기본 1MB), SSE 응답 대기 시간 늘리기
  - DB·FastAPI 포트를 서버 밖으로 열지 않음(nginx 80·443만)
  - `envs/example.prod.env` 최신화(LLM 키·파일 저장 설정 추가, `REDIS_PORT`·`AI_WORKER_VERSION`·`COOKIE_DOMAIN` 정리)
- `app/Dockerfile`의 uvicorn 프로세스 수(`--workers 3`)는 운영진 답변(인스턴스 사양)과 메모리 측정 결과로 다시 정합니다. (안건 2의 AI 워커 컨테이너와는 다름)

### 안건 2. AI 워커 컨테이너·Redis

- 추천안: 첫 배포는 BackgroundTasks로 가고 `ai-worker`·`redis`는 compose에서 뺍니다.
  - 이유: 사용하는 코드 없음(`ai_worker/`는 템플릿), 요구사항에도 없음(REQ-NFR-002는 2차, async/await·동시 호출 10건 제한), 재시작 문제는 시간 초과 처리로 보완(OCR 90초 명세 6-1, 가이드 30초 명세 7-1)
- 멘토님은 아키텍처 어필을 위해 두는 쪽을 권하셨으므로(2주차 멘토링 3), 무조건 빼지 않고 측정 결과로 정합니다.
- 2차로 옮기는 길: 명세 7-7대로 `run_guide_generation(guide_id)`를 그대로 AI 워커에서 부르면 됩니다(`run_scan_job()`도 같음).
- Redis는 2차 캐싱(REQ-NFR-013)을 고도화 주간에 구현할 때 다시 검토합니다.
- 로컬에서 `docker stats`로 OCR·가이드 생성 중 메모리를 재서 12/9(수)까지 AI 워커 컨테이너 여부와 uvicorn 프로세스 수를 결정합니다.

### 안건 3. 처방전 파일 저장과 정리 작업

- 추천안: 파일 저장을 로컬 폴더/S3 중 설정 값으로 고르게 만들고, S3 사용은 운영진 답변(S3 권한)을 듣고 정합니다. 권한이 없으면 서버 볼륨에 저장합니다.
  - 원본 파일은 확정 즉시, 미확정이어도 3시간 뒤 삭제(REQ-NFR-004)하는 임시 파일이라 서버 볼륨이어도 됩니다.
  - 원본 이미지는 S3여도 지금처럼 API(`GET /scans/{scan_id}/pages/{page_no}/image`, 인증, `no-store`)로만 내려줍니다.
- 이미 있는 코드: `scan_service.py`의 `FileStore` 프로토콜, 정리 작업 함수 `run_cleanup()`
  - 만들 것: `FileStore` 구현(저장·읽기·삭제, 로컬·S3), 정리 작업을 10분마다 돌리는 부분(지금은 부르는 곳이 없음)
  - uvicorn `--workers 3`이라 FastAPI 안에서 돌리면 세 번 돌므로, 같은 이미지로 정리 작업만 돌리는 compose 서비스를 따로 둡니다.
  - ERD `document_pages.file_path`·`image_path`에는 저장 위치(로컬 경로 또는 S3 키)를 넣습니다. ERD 변경 없음
- 업로드 기준은 요구사항(REQ-OCR-001)·명세 1번 그대로(파일 1개 10MB, 합계 30MB, 10장). 30MB는 10장 합계 기준이고, 프론트에서 올리기 전에 사진 크기를 줄입니다.
- 이재경·이채민이 `FileStore` 함수 모양을 먼저 맞춘 뒤 시작합니다(이채민 `scan_repository` 작업과 겹치지 않게).
- 논의:
  - 전원 찬성
