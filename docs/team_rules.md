## 1. 기본 마음가짐

1. 모르는 건 부끄러운 게 아니라 **늦게 말하는 게** 문제예요. 막히면 혼자 오래 붙잡지 말고 바로 공유해요.
2. 코드 리뷰는 **사람이 아니라 코드**에 대한 의견이에요. 부드럽게 말하고, 열린 마음으로 받아요.
3. 내 작업이 다른 사람의 일정에 영향을 줄 수 있다는 걸 기억해요.
4. 결정된 사항은 반드시 기록으로 남겨요. (회의록 · 노션 · GitHub 이슈)

## 2. 소통

### 채널별 용도

| 채널 | 용도 |
| --- | --- |
| Discord | 일상 소통, 질문, PR·리뷰 알림 |
| Notion | 회의록, 요구사항 정의서 등 산출물 |
| GitHub Issue | 작업 단위 관리, 버그 기록 |

### 응답 규칙

1. 코어 타임(수업 시간)에는 Discord 메시지에 가능한 한 빨리 반응해요.
2. 바로 답하기 어려우면 이모지로 "확인했어요"만이라도 남겨요.
3. 코어 타임 외 시간에는 답장을 강요하지 않아요. 급한 일은 멘션(@)으로 알려요.

### 부재 · 지각 공유

1. 결석, 지각, 조퇴, 개인 사정으로 작업이 어려울 때는 **미리** Discord 일정 공유 채널에 알려요.
2. 맡은 작업이 밀릴 것 같으면 기한 전에 공유해서 함께 조정해요.

## 3. 회의

### 데일리 스크럼 (초안)

- 시간: 매일 (작성 예정) / 약 10~15분
- 각자 아래 세 가지를 짧게 공유해요.
  1. 어제 한 일
  2. 오늘 할 일
  3. 막힌 부분 · 도움이 필요한 부분

### 정기 회의

- 주기: (작성 예정)
- 회의록은 `docs/meetings/YYYY-MM-DD_회의록.md` 형식으로 남기고, 노션에도 같은 내용으로 작성해요.
- 회의록 작성자는 (돌아가면서 / 고정 담당) 정해요. → 채민님

### 회의 진행 규칙

1. 회의 전에 안건을 미리 올려요.
2. 한 사람이 말할 때는 끝까지 들어요.
3. 회의가 끝나기 전에 **결정 사항과 담당자, 기한**을 꼭 정리해요.

## 4. 의사결정

1. 기본적으로 **충분히 논의한 뒤 합의**로 정해요.
2. 의견이 갈리면 각 의견의 장단점을 정리하고 **다수결**로 정해요.
3. 그래도 결정이 어렵거나 시간이 촉박하면 **해당 파트 담당자 → 팀장** 순으로 최종 결정해요.
4. 한 번 정한 사항을 바꾸려면 이유를 공유하고 다시 합의해요.

## 5. Git · GitHub 규칙

### 브랜치 전략

```
main        배포용 (직접 push 금지)
└─ dev      개발 통합 브랜치 (직접 push 금지)
   └─ feat/이슈번호-기능명    예) feat/12-medication-guide
   └─ fix/이슈번호-버그명     예) fix/15-login-error
   └─ docs/문서명           예) docs/readme
```

1. 작업은 항상 **최신 `dev`에서 브랜치를 새로 따서** 시작해요.
2. `main`과 `dev`에는 직접 push하지 않고, 반드시 PR로 머지해요. (push 못 하도록 막아 두었습니다!)
3. 머지가 끝난 브랜치는 삭제해요.

### 커밋 메시지

```
태그: 작업 내용 요약 (한글 OK)
```

| 태그 | 의미 |
| --- | --- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 |
| `refactor` | 코드 리팩토링 (기능 변화 없음) |
| `style` | 코드 포맷팅, 세미콜론 등 (동작 변화 없음) |
| `test` | 테스트 코드 추가 · 수정 |
| `chore` | 빌드, 패키지, 설정 파일 등 기타 |

예시: `feat: 복약 안내 생성 API 추가`

1. 커밋은 **작은 단위로 자주** 해요.
2. 한 커밋에는 한 가지 작업만 담아요.

### 이슈

1. 작업을 시작하기 전에 이슈를 먼저 만들고 본인을 담당자(Assignee)로 지정해요.
2. 이슈 제목은 `[태그] 작업 내용` 형식으로 써요. 예) `[feat] 진료 기록 입력 폼 구현`

### PR (Pull Request)

1. PR 제목은 커밋 메시지와 같은 형식으로 써요.
2. PR 본문에는 **관련 이슈 번호, 작업 내용, 확인 방법, 스크린샷(화면 작업일 때)** 을 적어요.
3. PR이 올라오면 Discord로 알림이 가요. 재리뷰 요청 시 리뷰어가 멘션돼요.
4. 머지 전에 **최소 1명 이상의 승인(Approve)** 을 받아요.
5. 머지는 **리뷰어가** 승인 후 머지까지 진행해요.
6. 충돌(conflict)은 PR을 올린 사람이 해결하고, 어려우면 바로 도움을 요청해요.
7. 리뷰어 마니또는 매주 변경되어요. **Discord 팀 공지**를 확인해주세요!

## 6. 코드 리뷰

### 리뷰어

1. PR 알림을 받으면 **12시간 안에** 리뷰를 시작해요.
2. 아래처럼 의견의 무게를 앞에 붙이면 받는 사람이 판단하기 쉬워요.

| 표시 | 의미 |
| --- | --- |
| `[필수]` | 꼭 고쳐야 하는 부분 (버그, 보안 문제 등) |
| `[제안]` | 고치면 더 좋은 부분, 반영 여부는 작성자가 판단 |
| `[질문]` | 이해가 안 돼서 묻는 것 |
| `[칭찬]` | 좋았던 부분 👏 |

3. "이거 왜 이렇게 했어요?"보다 "이렇게 하면 어떨까요?"처럼 말해요.
4. 승인 시 approve 코멘트 후 머지
5. 수정 사항이 필요할 때는 Request Changes로 머지를 막아주세요!
    - 재리뷰 요청이 오면 확인 후 approve로 승인 -> 머지 진행 해주세요.

### 작성자

1. 리뷰 의견에는 반영 여부와 관계없이 답글을 남겨요.
2. 반영했다면 어떤 커밋에서 고쳤는지 알려줘요.

## 7. 코드 · 보안

1. 코드 스타일과 포매터는 기술 스택이 정해지면 정해요. → (작성 예정)
2. **API 키, 비밀번호, DB 접속 정보는 절대 커밋하지 않아요.** `.env` 파일로 관리하고 `.gitignore`에 꼭 넣어요.
3. 실수로 비밀 정보를 올렸다면 **바로 팀에 알리고** 운영진에게도 알려요!!!!!!!!!

## 8. 갈등이 생겼을 때

1. 불편한 점은 쌓아두지 말고, 가능한 한 빨리 **당사자에게 직접, 정중하게** 이야기해요.
2. 둘이서 해결이 어렵다면 팀장에게 이야기하고 함께 방법을 찾아요.
3. 감정이 아니라 **상황과 사실** 중심으로 이야기해요.
