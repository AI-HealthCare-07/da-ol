## 3. 아키텍처 · 배포

- **AI 워커 + Redis 유지 여부**
  - MVP라 꼭 필요하진 않지만, "아키텍처까지 고려했다"를 어필하려면 두는 게 좋음
  - 워커: AI 작업이 백엔드 서버 메모리를 차지해서 다른 요청과 겹쳐 서버가 터지는 걸 막으려고 분리
  - Redis: 주로 캐시 (같은 질문, 무거운 페이지를 미리 저장해 두고 빠르게 응답)
  - ⚠️ 서버가 늘면 비용 증가. 심사위원이 "MVP에 왜 썼냐, 오버엔지니어링 아니냐"고 물을 수 있으니 **"백엔드 서버 부담을 덜려고 워커를 분리했다"는 이유를 말할 수 있게 준비**
- **모놀리식 vs MSA**
  - 모놀리식: 서버 하나에 DB·Redis까지 다 둠 (EC2 한 대에 FastAPI + PostgreSQL = 모놀리식)
  - MSA: 서버를 나눠서 하나가 꺼져도 나머지는 동작
  - 비용이 넉넉하면 AWS PaaS(관리형 DB·Redis)를 쓰는 쪽이 더 안정적, 아니면 모놀리식에 서버 사양만 조금 올려도 됨. MVP는 웬만하면 다 돌아감
- **서버 사양 고민은 AWS 계정이 나온 뒤에**: 그때 로컬에서 서버를 오래 돌려 메모리 추이를 보고 EC2에서도 비교
- **파일 업로드는 AWS S3에**: 처방전 파일은 서버 컴퓨터가 아니라 S3 저장소에 올리는 게 일반적
  - 30MB 업로드가 꼭 필요한지도 질문하심 (5장 PDF가 15MB 정도인 건 고화질 이미지 때문일 것, 보통은 그렇게 크지 않음)
- **Vercel은 비추천**: 제약이 많고 CORS·쿠키 설정이 복잡하며 개발자가 제어하기 어려움. 보통 보여 주기용 홈페이지에 씀
  → 프론트도 AWS 컨테이너로 띄우는 걸 추천 (백엔드·프론트·워커 각각, Redis는 PaaS 또는 백엔드 안에). 프론트는 메모리를 많이 안 먹어서 비용 부담이 크지 않음
- **DB 마이그레이션**: Claude가 Alembic 파일을 만들어 알아서 할 것. 버전 관리만 잘하면 롤백도 쉬움
- **API 확인**: FastAPI의 **Swagger(`/docs`)**에서 구현한 API를 직접 테스트하고, 기능 명세서와 맞는지 확인하기

## 5. AI로 개발할 때 어디까지 이해해야 하나

- 로그인·인증 같은 걸 과정 중에 다 알고 가는 건 불가능 (예전엔 인증 담당자가 따로 있을 정도로 큰 파트)
- 대신 **발표 때 물어보면 원리는 설명할 수 있어야** 함
  - 예: 토큰을 어떤 방식으로 인증하는지, 어디에 저장하는지, 어떻게 복호화하는지
- 꼭 머리에 있어야 하는 건 **아키텍처** (모놀리식 vs MSA, Redis를 왜 쓰는지 등). 업계에서 가장 몸값이 비싼 것도 아키텍트
- 백엔드는 기획·설계만 잘하면 AI가 잘 짜 줌. 요즘은 사람 개입 없이 개발하는 방향으로 가고 있음
- **공부 방법**
  - Claude가 작업하는 동안 놀지 말고 계속 물어보기: "왜 이렇게 했어?", "이 기능엔 어떤 값이 들어와?"
  - **`/eli5`**: 어려운 걸 쉬운 HTML로 설명해 주는 스킬. 작업 하나 끝날 때마다 돌려 보기
  - **`/btw`**: 작업이 도는 중에도 "지금 만드는 거 뭐야?"처럼 옆에서 질문하기
  - (멘토님이 디스코드 #멘토링 채널에 공유해 주심)
  - 겁내지 말고 AI로 여러 개를 빨리 만들어 보기, 영어 공부하기
- **트렌드 따라가기**: 링크드인(LLM 관련 사람 팔로우), 스레드, X(트위터), 레딧, 유튜브(코딩팩토리, 개발동생, 코딩애플 등). 아침저녁으로 피드만 봐도 충분
