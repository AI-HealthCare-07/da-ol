# 📝 1주차 멘토링 정리

## 1. 부트캠프 기간에 무엇을 공부할지
- 개발은 AI가 대부분 해 주니까, 이 기간에는 **아키텍처와 시스템 설계** 쪽을 중점적으로 공부하는 게 좋음. 그래야 AI에게 제대로 시킬 수 있음
- 다만 코딩 테스트가 아직 있으니 기본적인 코드는 칠 줄 알아야 함
- 의료 전공자가 있는 건 큰 장점. 사용자 입장에서는 "이 도메인에 맞는 UX가 뭘까", 개발자 입장에서는 "어떻게 하면 더 빠르고 효율적으로 만들까"를 고민하기

## 2. 기획 설명과 시장 조사
- 왜 이 프로젝트를 했는지, 어떤 문제를 푸는지, 다올이라는 이름의 뜻, UI 흐름을 설명함
- 당시에는 처방전 외에 퇴원기록지 같은 진료 기록과 PDF까지 받고, 의약품 공공 API와 연동한다고 설명함
- **시장 조사·경쟁사**: 실리콘밸리에서도 비슷한 당뇨 관리 앱이 엑싯한 사례가 있고, 해커톤에서도 개인 건강 관리 앱이 아주 많이 나옴 → 비슷한 서비스와의 차별점을 꼭 파악하기
- **사업성 여부**: 사업성을 봐야 하는 프로젝트인지 운영진께 확인해 보기. 사업성(BM)은 개발보다는 발표 때 녹이는 부분
- **차별점에 대한 지적**
  - 복약 체크 버튼을 사용자가 정말 누를지부터 고민해야 함 ("나도 안 하는 걸 사용자가 할까?")
  - 약봉투나 약 목록을 보여 주는 건 너무 당연한 기능이라, 그것만으로는 필요한 서비스인지 물음표
  - 데이터는 활용하되, 한 단계 더 나아간 브레인스토밍이 필요함

## 3. 웹 vs 앱
- 웹 서비스로 가도 상관없지만, 완성도가 높아 보이려면 앱이 나음
- 주제는 바꿀 수 없으니 추가 차별점을 넣어서 어필해야 함

## 4. OCR과 LLM 선택
- CLOVA OCR 말고도 선택지가 많고, 요즘은 Claude·GPT 같은 멀티모달 모델로도 글자 인식이 충분히 됨
- **CLOVA OCR과 Claude Haiku(멀티모달)의 비용·성능을 비교 테스트**하기
- 이유: 발표 때 "얼마나 시도했고, 어떤 가설을 세워 검증했고, 그래서 이걸 골랐다"는 근거가 있어야 AI 프로젝트로 설득력이 생김

## 5. RAG가 필요한가
- 데이터가 처방전·PDF 정도라면 RAG가 꼭 필요하진 않을 수 있음 (RAG는 문서가 수백~수천 개일 때 유사도로 찾는 방식)
- 약 정보는 공공 API로 가져오니 function calling으로 충분할 수 있음
- 다만 약의 효능·성분 같은 **의미 정보**는 검색이 필요할 수 있어서, 그 부분엔 RAG가 필요할 수도 있음
- 벡터 DB는 Chroma를 따로 쓰지 말고 **PostgreSQL + pgvector** 하나로, 그 안에서 하이브리드 검색하기

## 6. 가이드라인 데이터 정제 (중요)
- PDF를 통째로 넣지 말고 반드시 **정제해서** 넣기
- 파서·랭체인으로 자동 변환하기보다, 손이 많이 가더라도 **마크다운으로 직접 정리**하는 게 성능에 가장 좋음
- 쓸데없는 태그는 지우고, 필요 없는 내용은 쳐내고, 요약할 수 있는 건 요약하기 → **토큰 절약에도 효과적**
- 데이터 범위는 일단 모을 수 있는 걸 최대한 모아 본 뒤 결정. 한 번에 다 하려 하지 말고 범위를 좁혀 하나씩 되는지 확인하며 넓히기. 안 되면 과감히 포기하고 UX로 보완
  - 선택지를 사용자에게 보여주는 형식 (고객센터 챗봇 들어가면 어떤 유형의 질문인지 FAQ 누르라고 하는 것처럼)

## 7. Reranker 대신 Jev
- 하이브리드 검색 + reranker도 좋지만, 멘토님이 직접 테스트해 보니 **판단 모델 Jev가 reranker보다 재정렬 성능이 더 좋았음**
- BGE reranker는 오픈 모델이라 EC2에 직접 띄워야 하는데, 자원도 모르고 서빙도 만만치 않음 → **SaaS API를 쓰는 게 나음**
- Jev 원리: 질문과 검색된 문서를 넣으면 관련 있어 보이는 문서를 확률값으로 뽑아 줌 → 그 확률로 순서를 다시 매김

## 8. 토큰 절약과 LLM Wiki
- 요즘 회사들이 토큰 비용 절감에 관심이 많아서 **토큰 절약도 심사 포인트**가 될 수 있음
- LLM Wiki는 목차(인덱스)를 트리처럼 만들어 찾는 방식이라 토큰이 좀 더 듦 → RAG를 먼저 구축하고, 성능이 안 나오면 Wiki 고려

## 9. 에이전트와 function calling
- 요즘 현업은 **ReAct 에이전트** 기반 (Claude Code, Codex도 같은 구조). 그 근간 기술이 **function calling**
- **에이전틱 RAG가 일반 RAG보다 성능이 훨씬 나음**
  - 벡터 DB를 하나의 도구로 두고, 에이전트가 스스로 무엇을 검색할지 생각하고 계획함
  - 일반 RAG는 맞는 정보가 없으면 거기서 끝나지만, 에이전트는 다른 검색을 다시 시도할 수 있음
  - 요즘은 일반 RAG를 거의 안 씀
- 숙제: **랭체인 ReAct 에이전트와 function calling 실습**, LLM 답을 JSON으로 뽑아 서비스와 연결하는 테스트

## 10. 응답 시간 목표
- **가이드 생성 20초**: 데이터 전처리만 잘해 두면 충분히 가능
- **챗봇 첫 글자 3초**: 모델에 따라 속도가 달라져서 목표로서 큰 의미는 없을 것 같음

## 11. 개인정보와 위험한 표현 막기
- 개인정보는 기본적으로 다 마스킹. 원본 파일 관리는 거버넌스 문제라 "이렇게 관리한다"고 설명만 하면 됨
- **위험한 표현 막기**
  1. 프롬프트를 아주 많이 다듬고 엣지 케이스를 계속 테스트
  2. 프롬프트 버전별 결과를 엑셀로 관리
  3. 그래도 부족하면 답변이 나가기 전에 LLM을 하나 더 둬서 걸러내는 단계 추가 (대신 느려지고 비용 증가)

## 12. 알림과 앱
- 복약 알림은 당연히 넣어야 함
- 웹은 휴대폰 알림이 어려우니 이메일, 문자, 에이전트 전화 같은 방식을 벤치마크해 보기
- 웹을 먼저 만들고 앱까지 연결해서 보여 주는 게 가장 좋음

## 13. 범위와 개발 도구
- 요구사항 80개는 많지 않음. 우선순위를 나눴으니 핵심부터 개발하고, 시간이 남으면 살을 붙이기
- IDE는 현업에서 VS Code를 가장 많이 쓰고 PyCharm은 거의 안 씀. Claude Code, Codex, Gemini Antigravity 같은 AI 개발 환경을 써 보는 연습 추천
- 개발할 때는 Sonnet 이상 모델 권장

## 14. 숙제
1. Claude Code 써 보기, **Skills·MCP 개념 공부**
   - MCP: 도구를 쓰는 규격화된 프로토콜
   - Skill: 프롬프트와 스크립트로 에이전트에게 사용법을 알려 주는 것
2. **데이터를 모아 정리하고 디스코드에 올리기** (양을 보고 RAG 수준을 함께 판단)
3. **RAG 테스트**: 랭체인, LlamaIndex, Google ADK, AutoGen 등을 성능·유지보수 기준으로 비교해 고르고, **평가 데이터를 만들어 검증**까지 하기
4. **AWS CLI로 터미널에서 접근 가능한지** 확인 (모르면 운영진께 문의)

## 15. 그 밖에
- 기획이 바뀌면 디스코드·노션에 계속 올리기. 멘토링 시간이 아니어도 보고 피드백해 주신다고 함
